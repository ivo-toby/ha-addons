# Talon Home Assistant add-on

## Quick installation: Codex + Telegram

1. In Home Assistant, open **Settings → Add-ons → Add-on Store → ⋮ → Repositories** and add `https://github.com/ivo-toby/ha-addons`. Install **Talon** from this repository.
2. Leave the add-on options `instance` and `storage_path` empty for a first installation. Start Talon and select **Open Web UI** to access its management terminal.
3. Check the daemon with `talonctl status`. Sign in to Codex using `codex login --device-auth` and follow the displayed instructions. Verify with `codex login status`.
4. Configure Codex as the agent provider. **The `--enabled` flag is required:** without it, newly added providers are disabled by default, and setting the default provider or testing it will fail:

   ```sh
   talonctl add-provider --name codex --type codex-cli --command codex --enabled
   talonctl set-default-provider --name codex --context agent-runner
   talonctl set-default-provider --name codex --context background
   talonctl test-provider --name codex --context agent-runner
   ```

   **Existing installations:** if `talond.yaml` has `type: cli` under `agentRunner.providers.codex` or `backgroundAgent.providers.codex`, change both to `type: codex-cli` and restart the add-on. Talon's daemon only registers provider types with a matching factory; `cli` is not a registered factory type, so Telegram may fail with `No enabled agent runner provider is configured` even when `test-provider` succeeds. Back up the YAML first. Do not delete threads or reset Codex authentication for this error.

5. Create the assistant persona **with Codex and its model explicitly selected at creation time**:

   ```sh
   talonctl add-persona --name assistant --model gpt-6.1-sol --provider codex
   talonctl list-personas
   ```

   The model must be available to the installed Codex CLI and your ChatGPT account. `gpt-6` may return `model_not_found` with ChatGPT-backed Codex authentication; verify the model with a direct Codex test and adjust the persona model if necessary. The sample uses `gpt-6.1-sol`, verified in one Codex CLI 0.159.0 installation using ChatGPT authentication; availability may differ by account or CLI version. Verify with `codex exec --skip-git-repo-check "Antwoord uitsluitend met OK"` and use the model shown in its output.

   **Before restarting the add-on**, fix the relative system prompt path sometimes generated by `add-persona`. This command changes only the known default-workspace path and makes a backup; it fails if neither the relative nor the expected absolute path is present:

   ```sh
   node <<'NODE'
   const fs = require('fs');
   const p = '/data/talon/workspaces/default/talond.yaml';
   const s = fs.readFileSync(p, 'utf8');
   const relative = 'systemPromptFile: personas/assistant/system.md';
   const absolute = 'systemPromptFile: /data/talon/workspaces/default/personas/assistant/system.md';
   if (!s.includes(relative) && !s.includes(absolute)) throw new Error('Unexpected systemPromptFile path; inspect talond.yaml');
   if (s.includes(relative)) {
     fs.copyFileSync(p, p + '.bak');
     fs.writeFileSync(p, s.replace(relative, absolute));
   }
   console.log('System prompt path verified.');
   NODE
   ```

   For named workspaces, use that workspace's absolute path. Ensure the referenced file exists. The startup validator rejects relative system prompt paths.

   The `--model` and `--provider` flags are supported by Talon's `add-persona` command. **Do not omit either flag:** without them the persona may use Claude defaults, even if Codex is the global default provider. The provider name must match the one created in step 4 (`codex`). If `assistant` already exists, do not run `add-persona` again; inspect the existing persona and update its `model` and `provider` fields in `talond.yaml` as needed. Keep its other settings and system prompt unchanged.

6. In Telegram, open **@BotFather**, send `/newbot`, and copy the token it gives you. In Talon's terminal, run:

   ```sh
   talonctl add-channel --name telegram --type telegram
   ```

7. Enter the Telegram bot token securely from the add-on terminal. The command below updates the `botToken` value for the Telegram channel regardless of the placeholder generated by `talonctl add-channel`. It makes a backup and does not echo the token:

   ```sh
   read -rsp "Telegram bot-token: " TOKEN; echo
   TOKEN="$TOKEN" node <<'NODE'
   const fs = require('fs');
   const p = '/data/talon/workspaces/default/talond.yaml';
   const s = fs.readFileSync(p, 'utf8');
   const token = process.env.TOKEN;
   if (!token || !/^\d+:[A-Za-z0-9_-]+$/.test(token)) throw new Error('Invalid Telegram token format');
   const lines = s.split('\n');
   const start = lines.findIndex(l => /^\s*-\s+name:\s*telegram\s*$/.test(l));
   if (start < 0) throw new Error('Telegram channel not found');
   const end = lines.findIndex((l,i) => i > start && (/^\s*-\s+name:/.test(l) || /^[a-zA-Z][\w]*:/.test(l)));
   const stop = end < 0 ? lines.length : end;
   const index = lines.findIndex((l,i) => i > start && i < stop && /^\s*botToken:/.test(l));
   if (index < 0) throw new Error('botToken missing');
   lines[index] = lines[index].replace(/^(\s*botToken:).*/, '$1 ' + JSON.stringify(token));
   fs.copyFileSync(p, p + '.bak');
   fs.writeFileSync(p, lines.join('\n'));
   console.log('Telegram token updated.');
   NODE
   unset TOKEN
   ```

   This targets the default workspace; adjust the path for a named instance. Never paste your bot token into screenshots, logs, or GitHub. Do not assume that `talonctl add-channel` writes a literal `"\${TELEGRAM_BOT_TOKEN}"` placeholder.

8. Bind Telegram to the assistant and verify the saved configuration:

   ```sh
   talonctl bind --persona assistant --channel telegram
   talonctl list-channels
   talonctl list-providers
   ```

9. **Restart the Talon add-on from Home Assistant** to rebuild the daemon's provider registry. A `talonctl reload` hot-reload is not a substitute for a full restart after changing provider configuration. Run `talonctl status`, then open your bot in Telegram, tap **Start**, and send `Hello`. In the add-on logs verify `agent-runner: starting query` reports `provider: codex` and the bot actually replies. If the daemon opens only the recovery terminal, inspect startup logs and run `node /usr/local/lib/talon-check-config.cjs /data/talon/workspaces/default/talond.yaml /data/talon/workspaces/default /data/talon/workspaces/default/state` before restarting again.

**Troubleshooting:** If Telegram shows *typing* without replying, inspect the add-on logs for the provider actually handling the thread. An old thread may still be tied to `claude-code` even after Codex is set as default. Inspect with `talonctl list-threads --channel telegram` and, if appropriate, reset affinity using `talonctl reset-provider-affinity --channel telegram --all --yes`. If the add-on only opens a recovery terminal after restart, check the log's configuration-validation error: a missing file or invalid path can prevent the daemon from starting. Do not delete the workspace or database as a troubleshooting shortcut.

## Configuration

The add-on settings select **instance**, private **storage_path**, and **attachment_allowed_origins**. Model, provider credentials, Telegram tokens, channel recipients, and persona settings belong in the workspace's `talond.yaml` or the provider's supported authentication flow. Talon keeps the existing configuration across restarts.

By default, Talon stores its configuration, workspace, and database in private
persistent storage under `/data/talon`. Use `storage_path` to select another
absolute directory inside `/data`.

Set `instance` to the workspace name you want to open (for example, `example`).
Leaving it empty selects `default`. The instance setting selects one workspace;
it does not start additional Talon daemons. Existing workspace configuration
and skill definitions are reused without copying files.

Model, Telegram and other channel settings are edited only in `talond.yaml` in
the private add-on terminal (`$TALON_WORKSPACE`). Home Assistant settings do
not silently override or regenerate the file. Existing installations retain
any original model and Telegram configuration when updating the add-on.
The API key and Telegram token are exported as `OPENAI_API_KEY` and
`TELEGRAM_BOT_TOKEN` for configurations that reference them. A workspace using
another provider does not need a dummy API key.
Normal restarts and upgrades preserve this configuration.

Each named workspace receives its own `state` directory, SQLite database,
threads and internal communication sockets. The current default workspace uses
`/data/talon/workspaces/default/state`; older experimental installations may use
`/data/talon/state`. Always check the effective configured paths before migration. The `instance` setting
**selects** a workspace; this add-on still runs one daemon at a time.

If `talond.yaml` is invalid, the daemon stops but the ingress terminal stays
available for editing the private configuration and restarting the add-on.
Changing `storage_path` selects a different private directory; it does not
relocate files. Most users should keep the default. Advanced users moving an
existing workspace must back up its configuration and database first.

## Startup verification

Version 1.0.0 omits the explicit `HEALTHCHECK NONE` instruction. Docker stores
that instruction as a nonempty `Config.Healthcheck` object with `Test: ["NONE"]`.
Supervisor versions that treat any such object as an enabled check can remain
in `startup`: Docker does not execute a disabled check or emit its health events.
The Node base image supplies no check; CI verifies the resulting image metadata.
`startup: application` controls boot order, and `timeout: 60` is the stop timeout;
neither setting nor the daemon's `READY` log releases that wait.

The ingress proxy still accepts only gateway `172.30.32.2` by default. It passes
HTTP and WebSockets to ttyd on loopback port 7682, which launches an unprivileged
`talond` shell. No host ports or wider subnet access are required. The launcher
stays in the foreground and keeps the recovery terminal alive if the daemon
configuration is invalid or the daemon exits.

Build and exercise the **actual** HA build context on a disposable Linux Docker
host (the test creates and removes only its own named containers/network/volume):

```sh
docker build -t talon-haos:1.0.0-check talon
python3 talon/smoke-image.py talon-haos:1.0.0-check
```

The test requires subnet `172.30.32.0/24` to be unused; do not run it on the live
Supervisor host. It reproduces the old disabled-healthcheck metadata, evaluates
the pinned upstream state method, and checks HTML, an interactive WebSocket,
rejection of other source IPs, startup without an API key, persistent YAML/SQLite
state across restart, and the recovery terminal. This is transport validation;
it does not run Supervisor or validate real HA authentication/session routing.

After an operator installs/rebuilds 1.0.0, verify on Home Assistant itself:

1. Record `ha supervisor info` and `ha addons info <slug>`; version must be
   1.0.0 and state must become `started`.
2. With host Docker access, inspect the add-on container's `Config.Healthcheck`
   and `State`; expect no healthcheck and a running container. Inspect only those
   fields, not environment variables containing credentials.
3. Open **Web UI** from the authenticated HA session. Confirm the terminal page
   loads and its WebSocket upgrades with HTTP 101, then execute `talonctl status`.
4. Check Supervisor logs if the state still remains `startup`. Record the actual
   installed image ID/version and metadata before attributing it to this fix.

Image/CI success alone must never be reported as a verified fix on a live HA
installation. No CI job here deploys or publishes the image.

## External tools and files

The add-on does not mount Home Assistant's shared folders. Integrate external
services and files through configured MCP servers and Talon permissions.

## Shutdown

On a Home Assistant stop or upgrade the launcher sends SIGTERM to the daemon process group and waits for shutdown to finish, with an add-on timeout of 60 seconds. The launcher uses setpriv for the daemon and terminal without runuser session timeouts. The Home Assistant stop signal exits the launcher with code 0 after children have shut down. CI checks the launcher command and shutdown signal/wait handling; the disposable Docker image smoke test additionally verifies a clean daemon shutdown and container exit code 0. A live Supervisor stop still requires operator verification. Outstanding AI calls and queued work can still exceed the allowed shutdown time; they are not guaranteed to finish before Home Assistant terminates the container.

## Troubleshooting and earlier test installations

These notes are for users of pre-release test builds or advanced custom storage
setups. **A fresh installation requires no migration or IPC changes.**

If you previously installed an experimental add-on and want to retain its
workspace, first back up the private `/data` directory and its SQLite database.
The experimental 1.0.1 layout could share a state directory between named
workspaces. Verify the effective `storage.path`, `dataDir` and any absolute
persona paths in `talond.yaml` before reusing that data. Do not delete the
original until the new installation has been checked.

If a real directory already exists at `workspace/data/ipc/daemon`, the
launcher will not overwrite it with the internal CLI bridge symlink. Instead,
it keeps the recovery terminal available. This is an exceptional situation;
inspect and back up the directory before manually resolving the conflict.

The ingress proxy runs as the unprivileged `talond` user. Its supervisor restarts it after unexpected exits, without restarting the Talon daemon. On shutdown, the launcher stops the supervisor and its proxy child. Check add-on logs if ingress remains unavailable.
